## Incident Git — resets d'historique (2×, sept. 2026)

**Symptôme.** `git log` retombé sur `Initial commit` (84a8127) alors que les fichiers
de travail étaient intacts ; deux occurrences constatées.

**Cause établie (forensique).** Le sandbox restaure le worktree (patchset) mais pas
toujours le namespace `.git/refs` lors des cycles hibernation/re-provisionnement :
- `.git` réinitialisé/re-cloné (reflog repart de `clone`, refs `main`+branche à 84a8127) ;
- objets partiellement conservés (commits 914437c, f886933… toujours résolvables,
  `914437c` = dangling) ;
- aucun `reset`/`checkout`/`branch -D` exécuté par l'agent (reflog corroborant).

Autrement dit : perte de **pointeurs** d'historique, jamais d'**objets ni de fichiers**.
Contenu récupéré à 100 % (diff HEAD→sauvegarde vide avant chaque re-push).

**Précaution anti-récurrence (règle de session).**
1. `git push origin arena/01a0a22b-data` après CHAQUE commit (jamais de commit non poussé en fin de tour).
2. Début de session : `git log --oneline | head -3` + `git status --short` — si l'historique a reculé, STOP, diagnostiquer avant tout commit.
3. Aucun `reset --hard` / `checkout .` / `branch -D` sans validation explicite de l'utilisateur.
4. Jalons (PR, audit) : noter le SHA dans le rapport + tag si l'utilisateur valide.
5. Ce CHANGELOG est mis à jour à chaque jalon (source de vérité lisible même sans Git).
